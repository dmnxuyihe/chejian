# 计划管理数据库表修改建议

## 1. 当前处理原则

当前版本不修改现有 31 张业务表，也不增加字段。新增的年度调整、审批流程、月度交验、配件月计划和配件临修计划暂存于现有 `application_state.payload` JSON 中，用于业务演示和流程验收。

真实 JMIS、路局集团公司接口同步不在本次范围内。正式上线前应将下述 JSON 数据迁移为关系表，并保留迁移脚本和数据核对报告。

## 2. 建议新增表

### 2.1 `annual_plan_version` 年度计划版本

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| annual_plan_version_id | bigint PK | 版本主键 |
| plan_year | integer | 计划年度 |
| version_no | integer | 年初版、季度调整版序号 |
| version_type | varchar(16) | INITIAL、Q1、Q2、Q3、Q4 |
| status | varchar(16) | DRAFT、SUBMITTED、APPROVED、PUBLISHED、ARCHIVED |
| adjustment_reason | varchar(500) | 调整原因 |
| created_by / created_at | bigint / timestamptz | 创建信息 |
| published_at | timestamptz | 发布时间 |

唯一约束建议：`(plan_year, version_no)`。

### 2.2 `annual_plan_monthly_summary` 年度计划月度汇总

字段建议：版本、月份、机型、修程、年初计划数量、调整后数量、实际进车数量、工艺周期天数、测算交车月份。唯一约束建议为 `(annual_plan_version_id, plan_month, model_id, repair_program_id)`。

### 2.3 `plan_approval_instance` 和 `plan_approval_action`

`plan_approval_instance` 保存业务类型、业务主键、当前节点、当前状态、提报人和提报时间；`plan_approval_action` 保存审核、审批、驳回、发布意见及操作人。业务类型建议包括：

- MONTHLY_REPAIR_PLAN
- VEHICLE_TEMPORARY_REPAIR
- COMPONENT_TEMPORARY_REPAIR
- COMPONENT_MONTHLY_INSTALL_PLAN

审批记录不得覆盖更新，应追加动作记录以满足审计要求。

### 2.4 `monthly_verification_record` 月度交验记录

建议字段：车辆检修计划主键、委修段、交验日期、交验结果、交验单号、验收人员、备注、创建时间。建议唯一约束 `(vehicle_repair_id, verification_date)`。

### 2.5 `component_monthly_plan` 和 `component_monthly_plan_detail`

主表保存月份、上下车方向、版本、状态和发布时间；明细保存配件类型、人工计划数量、测算数量、匹配公里基准、已匹配数量。上车明细还应关联具体 `component_instance_id`，记录自动推荐顺序、人工调整原因和调整人员。

### 2.6 `vehicle_temporary_repair_plan`

建议字段：委修段、机型、车号、计划入段时间、计划上台时间、临修内容、方案附件主键、状态、当前审批实例、创建及更新时间。

### 2.7 `component_temporary_repair_plan`

建议字段：配件名称、适用机型、配件序列号、规格型号、计划入段时间、临修内容、方案附件主键、状态、当前审批实例、创建及更新时间。配件序列号在未关闭计划中应保持唯一。

### 2.8 `plan_attachment`

建议统一保存整车临修和配件临修方案附件元数据：业务类型、业务主键、文件名、MIME、文件大小、对象存储地址、SHA-256、版本号、上传人和上传时间。生产环境不建议继续把附件 Base64 保存在 JSON 字段中。

### 2.9 `external_plan_sync_log`

待外部接口确定后新增。保存来源系统、同步批次、请求编号、开始结束时间、成功/失败数量、错误摘要、重试次数和原始报文摘要。业务数据应使用外部唯一编号实现幂等。

## 3. 现有表建议增加的字段

数据库负责人允许改表后，可考虑：

- `vehicle_repair`：增加 `external_plan_id`、`plan_version_id`、`submitted_at`、`published_at`。
- `component_instance`：增加 `accumulated_mileage_km`、`last_installed_at`、`qualified_at`，用于真实公里匹配和先进先出。
- `approval_record`：若继续复用，应增加通用 `business_type`、`business_id`、`action_type`、`comment`，否则建议采用独立审批实例表。

## 4. 索引与约束建议

- 所有计划表建立 `(status, planned_entry_at)` 或 `(status, plan_month)` 索引。
- 审批动作建立 `(approval_instance_id, created_at)` 索引。
- 外部同步编号建立唯一索引。
- 数量和公里数字段增加非负检查约束。
- 上台时间不得早于入段时间。
- 已发布版本只允许通过新版本调整，不允许覆盖原记录。

## 5. JSON 数据迁移建议

迁移顺序：年度调整 → 配件月计划 → 整车临修 → 配件临修 → 月度交验 → 审批实例及动作。迁移完成后应比较每类记录数量、业务主键、状态、附件哈希和审批历史，并在确认无误后停止向 JSON 载荷写入对应集合。

当前 JSON 集合名称：

- `annualPlanAdjustments`
- `componentMonthlyPlanRecords`
- `temporaryRepairPlans`
- `componentTemporaryPlans`
- `monthlyVerificationRecords`
- `planApprovalFlows`
