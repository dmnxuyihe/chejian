# V0.1 最终整体验收报告

## 验收结论

当前版本可以完整演示第一版主业务链路：

计划建立 → 提交并生成该车辆20条任务 → 智能排程到具体人员及资源 → 发布 → 工班长同班组微调 → 作业人员开始/完成 → 自动生成待检 → 质量人员通过或不通过。

建议以“内存演示版”通过 V0.1 验收。真实数据库持久化和高级排程能力不在本次通过范围内。

- 系统管理员先对工具执行新增、编辑和合法删除，随后主链路仍可完成：通过。
- 新增车辆计划并提交：通过。
- 为新车辆独立生成 4 条构架和 16 条轮驱任务：通过。
- 自动排程无开放异常并正常发布：通过。
- 工班长同班组换人并保存调整原因：通过。
- 调整后人员开始和完成任务：通过。
- 完成任务只生成一条待检记录：通过。
- 质量人员处理为 `PASS` 并保存意见：通过。
- 技术人员展示和排程共用 `src/data/process.js`，4+16任务、18条FS和2880分钟 lag 一致：通过。

## 本轮主要修复

- 计划提交生成车辆级20条任务，并保护已提交计划。
- 排程异常、发布状态、负荷和资源占用按车辆隔离。
- 多车逐车排程避让其他车辆的工位、人员、设备和配件占用。
- 锁定及已执行任务在重排中保留真实时间和资源，版本与分配 ID 保持唯一。
- 人员请假、工班长班组限制和 `AUTO` / `MANUAL` 来源校验。
- 作业任务严格状态机、实际时间记录和重复操作保护。
- 质量确认限制为已完成且待检的任务，防止重复及越序处理。
- 页面风格、数据库结构、任务顺序和 FS 关系均未修改。

## 已知问题和验收边界

1. 所有业务数据仍保存在浏览器内存中；角色切换和页面重新渲染会保留，浏览器硬刷新会恢复初始化数据。
2. 当前多车排程采用逐车避让策略，可以保证已排资源不冲突，但不做多车全局最优求解。
3. 工位容量大于1的并行槽位算法尚未实现；当前初始化工位容量均为1。
4. `docs/构架_轮驱检修流程.xlsx` 中部分轮驱任务标准工时为空，代码中的演示时长需要业务方确认。
5. 用户指定的 `docs/构架_轮驱_完整初始化数据_30表.xlsx` 在当前项目中不存在。本轮无法对该工作簿做逐表核对；已核对现有 `docs/数据库.xlsx`、流程工作簿和 `src/data`。

## 下一版本建议

1. 先补充缺失的30表初始化工作簿并确认流程文件中的空白标准工时。
2. 接入正式数据库持久化和服务端权限，保持当前已验收字段与状态语义。
3. 再按业务优先级推进多车联合优化、工艺维护、作业记录和质量返修闭环。
